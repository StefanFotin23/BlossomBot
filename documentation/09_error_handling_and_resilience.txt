=========================================================
TECHNICAL DOCUMENTATION: ERROR HANDLING & RESILIENCE
=========================================================

1. INTRODUCTION
BlossomBot implements a multi-layer resilience strategy to handle AI downtime, rate limits, and network volatility without degrading the user experience.

2. AI DOWNTIME & RATE LIMIT HANDLING (HTTP 429/503)
- CUSTOM EXCEPTIONS: API errors are mapped to `GeminiOverloadedError`.
- IN-PLACE WORKER RETRIES: Background workers hold the user's conversation lock and retry internally (3s, 6s delays). This prevents "Line-Cutting" by newer messages during an overload.
- MANUAL EXTRACTION FALLBACK (GOD MODE): On the final retry attempt, or if Gemini is completely down, the bot switches to a **Manual Regex Filter Extractor**. This guarantees a product response even with 0% AI availability.

3. SLACK EVENT IDEMPOTENCY
To prevent double-ordering from Slack's automatic 3-second retries, the bot tracks `event_id` in Redis. Retries are silently dropped if the original is still processing.

4. LLM OUTPUT HARDENING
- JSON Sanitization: Aggressive Regex cleaning of AI output.
- Structural Validation: Ensures `text` and `intent` fields are present in AI tasks; repairs them if missing.
- Safe Defaults: Returns fallback JSON objects on any parsing failure.

5. INFRASTRUCTURE HEALTH PROBES
The `/healthz` endpoint aggregates health checks for RabbitMQ, Qdrant, and Redis. Failure triggers Kubernetes probes to take the pod out of rotation, protecting users from "Half-Broken" states.

6. LOGGING & OBSERVABILITY
Workers use unique IDs (`[W0]`-`[W9]`) to track task flow. Noisy third-party logs are suppressed to keep the focus on state-machine transitions and RAG metadata.
