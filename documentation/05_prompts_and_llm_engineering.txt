=========================================================
TECHNICAL DOCUMENTATION: PROMPTS & LLM ENGINEERING
=========================================================

1. INTENT ROUTING PHILOSOPHY
BlossomBot employs a Hybrid Two-Tier Intent Gateway. Instead of relying solely on expensive external LLM API calls, it routes queries locally via a sub-millisecond local GRU intent classifier, checking contextual state priors and applying semantic guardrails before delegating to Gemini.
- Local GRU Classifier (Tier 1): Classifies simple queries locally in <0.5ms. If the classifier yields highly confident results and passes semantic guardrails, it routes the message instantly without calling the external API.
- Bayesian Context Updates: Modifies raw GRU probability predictions by applying prior probability state weights derived from the user's current conversational state, boosting contextual state retention.
- Gemini HTTP API Integration (Tier 2): Queried directly via HTTP POST requests (eliminating external client library dependencies and minimizing deployment complexity) for complex or multi-intent requests.
- Defined States: Operates on a closed set of intents (e.g., `GREETING`, `SEARCH_PRODUCTS`, `PRODUCT_DETAILS`, `FINISH_ORDER`).
- Zero Temperature: Enforces `temperature: 0.0` to ensure highly deterministic outputs and eliminate hallucinations.


2. DYNAMIC FILTER EXTRACTION
Converting natural language ("I want cheap purple tulips, but no roses") into structured database queries (JSON).
- Dynamic Schema: At startup, the application reads the dataset and generates `schema.json` (containing exact valid categories, colors, etc.). This schema is injected into the LLM prompt, forcing Gemini to output database-compliant strings.
- Output Structure: The LLM returns a complex structured JSON containing:
  1. `filters`: The cumulative positive requirements.
  2. `negative_filters`: A set of exclusions (e.g., "no roses" -> `flowers_type: Rose`). This allows the system to build `must_not` clauses in the vector search.
  3. `semantic_query`: A text summary of desired product features.
  4. `mentioned_now`: A list of filter keys the user explicitly stated *in the current turn*.
  5. `insisted`: A list of filter keys the user is frustrated about or repeats (e.g., "too expensive" -> `price_max`).

3. SMART CONFIRMATION (YES/NO PARSER)
Traditional regex-based chatbots fail on conversational confirmations like "k", "yep", or "sure, I want 3".
- The `parse_confirmation` function utilizes a zero-temperature LLM prompt to classify the user's intent as `confirmed: true/false`.
- It simultaneously extracts a new `quantity` if the user adjusts their order during the confirmation step (e.g., "Yes, add 5 pieces").

4. HYBRID FORMATTING (TEMPLATES)
When returning product details, we avoid using the LLM to generate the final text. LLMs can hallucinate prices or details.
- Approach: Python scripts (`generate_hybrid_response`, `generate_detailed_product_info`) take the exact JSON metadata returned by Qdrant.
- They aggressively parse and clean the text (stripping raw HTML tags like "Body (HTML):") and format the data into clean, readable Markdown lists for Slack.
- This guarantees 100% data accuracy with zero latency for formatting.

5. DETERMINISTIC "SMALL TALK"
For general inquiries ("Who are you?", "Are you online?"), the system avoids expensive generation. It uses a zero-temperature LLM call simply to classify the question into predefined buckets (`IDENTITY`, `AVAILABILITY`, `HUMOR`). It then instantly returns a friendly, hardcoded string.
