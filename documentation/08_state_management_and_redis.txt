=========================================================
TECHNICAL DOCUMENTATION: STATE MANAGEMENT & REDIS
=========================================================

1. THE NEED FOR STATE MANAGEMENT
Unlike simple FAQ bots, BlossomBot requires conversational memory to track product history, filter scores, and shopping cart state across asynchronous messages.

2. REDIS INTEGRATION
- Key Structure: `user:{user_id}` for complete isolation.
- TTL: 24-hour expiration (`ex=3600*24`) to clear abandoned sessions.
- Idempotency Layer: `evt:{msg_id}` (10m TTL) to ignore Slack retries and prevent double-ordering.

3. STATE PAYLOAD STRUCTURE & SELF-HEALING
- `state`: Current state machine node.
- `history`: Previous interactions for LLM context.
- `filter_scores`: Dynamic relaxation weights.
- `cart`: Array of pending items.
- SELF-HEALING MECHANISM: Every read from Redis includes a "Structure Repair" layer that restores missing or corrupted keys (e.g., `None` -> `[]`), ensuring stability.

4. ATOMIC PERSISTENCE (TECHNICAL INTEGRITY)
- IMMEDIATE SAVING: `set_user_state` is called immediately after every significant data change (search results, cart additions, confirmations).
- SOURCE OF TRUTH: The bot works on a single, passed user-state object to prevent "State Clobbering" where parallel background tasks might overwrite each other's Redis updates.

5. FALLBACK MECHANISM (RESILIENCE)
If Redis is unreachable, the bot falls back to an in-memory Python dictionary (`_local_user_states`). While this doesn't support multi-pod scaling, it keeps the bot functional during downtime.

6. CONVERSATIONAL CHECKPOINTS (HARD RESET)
Order completion or manual restarts overwrite memory with a clean, empty dictionary to provide a fresh start for the next interaction.
