=========================================================
TECHNICAL DOCUMENTATION: QUALITY OF SERVICE (QoS) & CONCURRENCY
=========================================================

1. INTRODUCTION
BlossomBot is designed to handle "Traffic Bursts" that exceed the rate limits of external AI APIs (like Gemini). Instead of dropping requests or providing inaccurate fallbacks, the system implements a proprietary Quality of Service (QoS) layer that prioritizes consistency and accuracy over immediate response time.

2. THE SEQUENTIAL AI TASK QUEUE
To manage the 15-30 RPM (Requests Per Minute) limit of the Gemini Free Tier, the application utilizes an `asyncio.Queue` called `vital_task_queue`.
- Failure Interception: When a `GeminiOverloadedError` (HTTP 429) is caught during intent routing or filter extraction, the current execution is suspended.
- Background Buffering: The raw Slack payload and user context are wrapped into a "Task Object" and pushed into the queue.
- Sequential Processing: A dedicated `background_task_worker` monitors the queue and processes items one by one.
- Rate-Limit Resets: The worker introduces a forced 4-second delay between tasks, ensuring the Gemini API has time to recover before the next request is sent.

3. ATOMIC USER-LEVEL SEQUENCING (LOCKING)
High-load scenarios often lead to race conditions where a user's second message (e.g., "Confirm Order") is processed before their first message (e.g., "Add to Cart") if the first was queued due to rate limits.
- User-Level Locking: To solve this, we implemented a "Busy Flag" in Redis (`busy:{user_id}`).
- Sequencing Constraint: If a user has a task pending in the global queue, all subsequent messages from that specific user are automatically added to the queue, even if the Gemini API currently has available quota.
- Consistency Guarantee: This ensures that for every individual user, the "Conversational Timeline" is preserved in strict chronological order (First-In, First-Out), preventing logic errors like empty shopping carts or skipped confirmations.

4. USER TRANSPARENCY
Queuing messages can lead to user anxiety if they receive no feedback. 
- Dynamic Positioning: When a task is queued, the bot calculates the `queue_size` and provides a specific position (e.g., "Position 3 in queue").
- Wait Time Estimation: Based on the worker's average processing speed, the bot provides a time estimate (e.g., "Wait time: ~15 seconds").
- Keep-Alive Heartbeats: For waits exceeding 15 seconds, a separate background task is spawned to send periodic updates to the user, ensuring they remain informed of the processing status.
