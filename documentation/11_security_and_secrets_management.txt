=========================================================
TECHNICAL DOCUMENTATION: SECURITY & SECRETS MANAGEMENT
=========================================================

1. INTRODUCTION
Security is a foundational pillar of the BlossomBot architecture. Although currently deployed in a local development environment (Kind), the project adheres to production-grade security practices, particularly concerning the management of API keys, environment variables, and network isolation.

2. SECRETS MANAGEMENT IN KUBERNETES
Hardcoding sensitive information (like Slack Tokens or Gemini API Keys) into source code or Docker images is a severe security anti-pattern.
- Kubernetes Secrets: BlossomBot utilizes Kubernetes `Secret` resources (specifically Opaque secrets). The `secrets.yaml` file defines the `slack-credentials` object, which holds base64-encoded values.
- Environment Variable Injection: In the `chat-app` Deployment (`deployment.yaml`), these secrets are securely injected into the container at runtime using `valueFrom: secretKeyRef`. This ensures that even if the Docker image is inspected or leaked, the credentials remain secure within the cluster's etcd database.
- .env Architecture: For local, non-Kubernetes testing, the application utilizes the `python-dotenv` library, loading credentials from a `.env` file which is strictly ignored in version control via `.gitignore`.

3. INTERNAL NETWORK ISOLATION
The microservices architecture employs strict network isolation to minimize the attack surface:
- ClusterIP Services: Critical internal databases, such as Qdrant (Vector DB) and Redis (State Store), are exposed only via `ClusterIP`. This means they are completely inaccessible from the public internet and can only be reached by other pods running inside the Kubernetes cluster.
- Ingress Control: The NGINX Ingress Controller acts as the single point of entry. It is configured to explicitly route only specific HTTP traffic (the Slack webhooks to FastAPI, and the RabbitMQ management UI). All other internal ports are shielded.

4. DEPENDENCY AND RUNTIME SECURITY
- Minimal Base Images: The Dockerfile is built upon `python:3.11-slim`, significantly reducing the OS-level attack surface by excluding unnecessary system packages.
- Non-Root Execution (Best Practice): While not explicitly enforced in the current dev iteration, the architecture allows for dropping root privileges within the Docker container for production deployments.
- Offline Machine Learning: By forcing the SentenceTransformers to load models strictly from local disk (`HF_HUB_OFFLINE=1`), the application avoids making unauthorized outbound HTTP requests to download executable code or weights at runtime, preventing potential supply-chain vulnerabilities.
